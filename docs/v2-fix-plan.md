# V2.10.1 死碼與待修清單（改回以 V2 為主體修正）

使用者決定：V2 的視覺化 UI／UX 體驗較好，改回 V2.10.1 修正，不再以 V3 取代。本文件列出 V2 的死碼（可刪除）與待修缺陷，作為之後逐步修正的依據。

- 來源：`docs/v3-audit.md`（§1 覆寫鏈、§4 死碼）、`tests/legacy/`（V2 行為測試，`QUIRK:` 與 `KNOWN_LOSS`）、V3 移植時發現並記在 `CHANGELOG.md` 的 V2 錯誤。
- 行號都是 `legacy/app.zh-Hant.html`。`legacy/app.en.html` 在約 L2361 之後多約 8 行（en 獨有的 `v147-en-text-tidy`），修改時兩份都要改。
- 死碼的判斷在盤點時已用瀏覽器實測（建立專案後檢查元素是否存在、呼叫函式看實際開啟哪個對話框）。**刪除前每一項都要再用 `tests/legacy` 確認一次**，因為之後修改可能改變行號。

## 0. 工作方式

1. 修改 `legacy/app.zh-Hant.html` 與 `legacy/app.en.html`（兩份都改），再執行 `node tools/pack.mjs` 產生 `index.html`（第 2 行是 base64，不要直接改）。
2. 驗證：`npm run test:legacy`（單元與 golden）、`npm run test:legacy:e2e`（E2E）。黃金檔只能在有意的行為修正時更新，並寫進變更紀錄。
3. 一項一個 commit，修正前後各跑一次測試。
4. V2 的 React 殼層（`af20-shell` bundle）沒有原始碼，只能改它外面的 HTML／JS／CSS，或在殼層之後加補丁層。殼層透過「點擊隱藏的 V1 按鈕」驅動引擎（audit §4.1 列出的 42 個 id），**這些隱藏按鈕不是死碼，不能刪**。

## 6. 合併「功能方塊設計」與「電源架構設計」

### 6.1 V2.10.1 現況

兩者其實是**同一種圖**（方塊、接腳、線路、接點、文字框、區域框的資料結構相同），差別都靠「目前是哪個工作區」在程式各處分支：

| 面向 | 怎麼分的 | 位置 |
|---|---|---|
| 判斷依據 | 設計類型 `function`／`power` 對應 V1 的工作區 `circuit`／`current`，存在全域變數 `activeWorkspace` | L470、L474（建立／載入）、L547–550 |
| 分支數量 | `activeWorkspace` 出現在 43 行、64 處（其中 `==='current'` 25 處）；`type==='power'` 9 處；另有 `afFunctionMode()`（L1235）、`isFn()`（L3876）兩個各自的判斷函式 | 見 6.4 盤點 |
| 接腳模型（**最大差異**） | 功能方塊：接腳陣列由使用者自由管理（L1241「Function blocks own their port arrays」）。電源架構：仍用 V1 的「槽位」模型 `ioConfig`（輸入／輸出各幾個、位置 .25／.5／.75），每次重繪 `normalizeSlots()`（L451）依槽位**新增或刪除接腳** | `ioConfig` 出現在 16 行；`normalizeSlots`、`cleanIO`、`setIO`、`ioSettings` L451–456 |
| 欄位 | 電源方塊多「電源角色、電壓、電流、效率」；電源線多「電壓、電流」，線名提示不同（電源軌／支路名稱 vs 訊號名稱／匯流排標籤） | `currentNodeFields`、`currentEdgeFields`、`edgeLabel` |
| 預設值 | 電源檢視新方塊角色 `converter`、新線 `kind: power` 且有箭頭 | L319、L1913 附近 |
| 呈現 | 線色、選取色、方塊外觀、說明文字、狀態列名稱、匯出檔名（`current-architecture`／`circuit-architecture`） | 多處 |
| 功能落差 | 零件庫（被動元件、符號、連接器、LCD）只在功能方塊（殼層 `D.fn()`、`afFunctionMode`）；電壓色帶、負載警告只在電源 | L1235、L3876、殼層 bundle |
| 範本與殼層 | 兩組範本（`AF.variants`／`AF.power`）；React 殼層的啟動卡片、設計圖示、`managedDesignType` 選單都寫死兩種類型（無原始碼） | L966、L538、bundle |

使用者面的問題：同一套系統要畫兩張圖、兩邊不同步；功能圖不能直接標電壓；電源圖不能用零件庫；電源方塊的接腳會被槽位規則改掉。維護面的問題：每個功能都要想「兩個工作區各要不要」，64 處分支散在 30 幾層覆寫裡。

### 6.2 方案比較

| 方案 | 做法 | 優點 | 風險／成本 |
|---|---|---|---|
| A. 只合併引擎、保留兩種類型（**建議**） | 檔案格式與殼層都不動，設計仍是 `function` 或 `power`；但引擎只有一套：所有 `activeWorkspace` 分支收斂到一個 `designMode()`，電源也改用功能方塊的接腳模型，零件庫與電壓標註兩邊都能用。再加一個「切換為電源檢視／功能檢視」指令，**就地改設計類型**（資料相同，只換呈現與預設值），一個復原步驟 | 不改存檔格式、舊檔照開；殼層無原始碼也不用改；使用者得到「同一張圖兩種看法」 | 中：電源接腳模型要遷移（`ioConfig` → 接腳陣列），要以測試確認舊電源檔開啟後圖面不變 |
| B. 完全合併成一種類型（V3 的做法） | 檔案只剩 `function`＋`view` 欄位；載入時把 `power` 轉成 `function`＋`view: power`；啟動畫面與殼層只剩一張卡 | 概念最單純 | 高：存檔格式改版，舊版 V2 打不開新檔；殼層寫死的類型、圖示、範本清單都要用補丁層改（沒有原始碼） |
| C. 維持現狀，只同步功能 | 兩邊各自補功能 | 改動最小 | 分支只會越來越多，不解決維護問題 |

**建議 A**：維護面的好處（一套引擎）與使用者面的好處（同一張圖切換看法）都拿到，又不冒存檔格式與殼層補丁的風險。日後若真的要 B，A 做完後只剩「格式與殼層」這一步。
